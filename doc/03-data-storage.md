# 03. 데이터 저장 구조 및 파일명 규칙

## 데이터 폴더 위치
데이터 폴더는 실행 폴더에 고정되지 않고 **사용자가 최초 실행 시 지정**한다. 지정 경로는 `%APPDATA%\ImageTopicViewer\settings.json`에 저장되어 이후 자동으로 사용된다. 상세 절차는 `02-architecture.md`의 "데이터 폴더 위치" 절 참조.

이 문서 전체에서 `.data`는 이 사용자 지정 데이터 폴더를 가리키는 표기다(실제 폴더명이 `.data`라는 뜻이 아님).

## 폴더 구조
```
{사용자 지정 데이터 폴더}/
├── {대주제1}/
│   ├── {소주제1}/
│   │   ├── {대주제1}_{소주제1}_001.png
│   │   ├── {대주제1}_{소주제1}_002.png
│   │   └── ...
│   └── {소주제2}/
└── {대주제2}/
    └── ...
```

## 파일명 규칙
`{대주제}_{소주제}_{번호}.png`
- 번호: 3자리 숫자, 1부터 순차 증가 (001, 002, 003...)
- 확장자: **항상 `.png` 고정**. 원본 확장자와 무관하게 저장 시 PNG로 통일 변환한다 (아래 "지원 이미지 포맷" 참조).

## 순서-파일명 동기화 (재넘버링) 로직
이미지 순서가 바뀌는 모든 경우(신규 추가, 드래그로 순서 변경, 삭제)에 대해 해당 소주제 폴더 내 파일을 **현재 표시 순서 기준으로 001부터 재넘버링**한다.

처리 순서 예시:
1. 새 순서 목록(ImageItem 리스트)을 확정한다.
2. 임시 파일명(예: `.tmp_{guid}`)으로 전체를 먼저 rename한다 (번호 충돌 방지).
3. 새 순서대로 001, 002, 003... 최종 파일명으로 rename한다.

> 파일이 많아질 경우 매번 전체 재넘버링은 비용이 커질 수 있음 — v1에서는 단순성 우선, 성능 이슈 발생 시 최적화 검토 (`08-open-decisions.md` 참조).

## 지원 이미지 포맷 및 포맷 통일 (확정)
확장자 허용 목록 대신 **디코딩 가능 여부**를 기준으로 판단한다: 드롭된 이미지 데이터를 디코딩할 수 있으면 받아들이고, 저장 시 항상 **PNG로 통일 변환**한다. 확장자가 무엇이든(웹 브라우저 드래그드롭 등으로 포맷이 제각각인 경우 포함) 결과 파일은 항상 `.png`가 된다. 디코딩에 실패하면 지원하지 않는 이미지로 간주하고 무시 + 안내 메시지를 표시한다.

- PNG를 선택한 이유: 무손실 압축, 투명도 지원, WPF(`BitmapDecoder`/`PngBitmapEncoder`)에서 추가 코덱 없이 기본 지원. 사진처럼 복잡한 이미지는 JPEG 대비 파일 크기가 커질 수 있음(v1은 용량보다 일관성/화질 우선).
- 최소 지원 예상 입력 포맷: `.jpg`, `.jpeg`, `.png`, `.bmp`, `.gif`, `.tiff` — WPF 기본 `BitmapDecoder`가 네이티브로 디코딩 가능.
- `.webp`, `.avif` 등은 WPF 기본 디코더가 지원하지 않으므로, 이 포맷들도 지원하려면 별도 디코더 라이브러리(예: 서드파티 WIC 코덱, SkiaSharp 등) 추가가 필요하다 — 구현 시점에 포함 여부 확인.

## 주제 이름과 파일명의 관계 (중요)
파일명에 대주제/소주제 이름이 포함되므로, **주제 이름이 변경되면 해당 폴더 내 모든 파일명도 함께 변경**되어야 한다. 상세 절차는 `04-topic-management.md` 참조.
